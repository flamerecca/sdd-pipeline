# 驗收規格範本：情境／操作／驗證 (Arrange-Act-Assert)

本文件提供以自然語言撰寫驗收規格的範本，讓 PM、QA 與工程師不需要學習 Gherkin 這種 `.feature` 檔專用語法與關鍵字規則，也能用同一份文件溝通規格。格式仍保留可直接對應到測試案例的三段式結構：情境 (Arrange)、操作 (Act)、驗證 (Assert)，工程師落地成單元測試或整合測試時，三個段落分別對應測試裡的三個區塊，不需要另外轉譯。

---

## 為什麼不用 Gherkin

Gherkin 的 `假如 / 當 / 那麼` 關鍵字與嚴格縮排規則，對不熟悉這套語法的 PM、QA 常常是額外的學習成本，寫規格時容易把心力花在「這句該用假如還是而且」，而不是規格本身要表達的業務邏輯。三段式的情境／操作／驗證用條列句直接寫，任何人看得懂中文就看得懂規格，對工程師而言仍然是同一組 Arrange-Act-Assert，落地成測試案例的成本沒有增加。

---

## 範本結構

```
## 情境名稱

**情境 (Arrange)**
- 條列出這個情境成立前，系統與資料應該處於的狀態

**操作 (Act)**
- 條列出使用者或系統實際觸發的單一動作

**驗證 (Assert)**
- 條列出這個動作發生後，應該觀察到的每一項結果
```

- 「操作」段落只放一個核心動作，不要把多個操作混在同一個情境裡，需要驗證的操作不同就拆成不同情境，這點與 Gherkin 建議「一個場景只驗證一件事」的精神一致。
- 「驗證」段落列出所有應該成立的結果，包含正常業務結果與需要一併確認的副作用，例如通知信是否送出、庫存是否連動扣減。

## 範例：會員購物車結帳流程

### 情境一：購物車有庫存時成功結帳

**情境 (Arrange)**
- 使用者已登入系統，帳號為 `user@example.com`
- 購物車內有 1 件商品「n8n 自動化課程」，單價 1200 元

**操作 (Act)**
- 使用者點擊「確認結帳」按鈕，並選擇信用卡付款成功

**驗證 (Assert)**
- 系統建立一筆狀態為 `Paid` 的訂單
- 系統發送一封訂單確認通知信至 `user@example.com`
- 購物車自動清空

### 情境二：商品庫存不足時結帳失敗

**情境 (Arrange)**
- 購物車內商品的庫存數量為 0

**操作 (Act)**
- 使用者點擊「確認結帳」按鈕

**驗證 (Assert)**
- 系統顯示錯誤訊息「商品庫存不足，無法結帳」
- 系統不扣除使用者任何金額

## 與測試程式碼的對應關係

三段式結構刻意對齊測試程式碼慣用的 Arrange-Act-Assert 寫法，工程師實作測試時可以逐段對照：

```
test("購物車有庫存時應成功結帳", () => {
  // Arrange：對應「情境」段落
  const user = loginAs("user@example.com");
  const cart = addItemToCart(user, "n8n 自動化課程", 1200);

  // Act：對應「操作」段落
  const order = checkout(cart, { payment: "credit_card" });

  // Assert：對應「驗證」段落
  expect(order.status).toBe("Paid");
  expect(sentEmails).toContainEqual({ to: "user@example.com", type: "order_confirmation" });
  expect(cart.items).toHaveLength(0);
});
```

規格裡的每一條條列項目，都應該能在測試程式碼裡找到對應的一行斷言或設定，找不到對應時代表規格寫得不夠具體，或測試漏掉了規格要求的項目。
